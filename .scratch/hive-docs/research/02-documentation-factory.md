# Documentation factory for a multi-cell hive

Researched 2026-09-12.

## Verdict

The factory is a **book assembler with one maintainer TOC**. It is not a website that also serves OpenAPI, rustdoc, or Swagger UI.

Handwritten sources: one table of contents, one entrypoint page (plain-language lead plus a one-page cell graph), one page per cell, short pages for kernel and `app`. The TOC links existing law (`docs/architecture.md`, ADRs), `CONTEXT.md`, and `CONTEXT-MAP.md`. It does not copy them.

Generated sources stay off that TOC:

| Artifact | Audience | How it is made |
| --- | --- | --- |
| Handbook | Hive maintainers | Handwritten Markdown, assembled by the factory |
| OpenAPI | API consumers | Generated from public REST presentation. Separate pipeline, separate publish |
| rustdoc | People reading Rust tokens | Generated from `///` / `//!` on public crate items. Optional third product. Not the handbook |

Do not pick mdBook, Docusaurus, or Antora as law. All three implement this shape: a TOC, per-module pages, a build command, a CI job that runs that build. Ticket 07 picks paths. Ticket 04 picks the gate contract. Ticket 03 picks the OpenAPI crate.

## Compared

### Docs-as-code tools (factory primitives)

Every mature assembler has the same four knobs. Names differ. The knobs do not.

| Knob | mdBook 0.5 | Docusaurus 3.10 | Antora 3.2 | Divio system |
| --- | --- | --- | --- | --- |
| TOC / entrypoint | `SUMMARY.md` is required. Without it there is no book | `sidebars.js` (or autogenerated from the docs folder). Docs-only mode can put the first doc at `/` | Playbook names `start_page`. Component `nav` key lists nav files in menu order | Four quadrants kept as separate sections. Collapse of those sections is the failure mode |
| Per-module pages | Numbered chapters, nested. Draft chapters (`[Title]()`) reserve a slot with no file | Plugin instance + sidebar category. One instance per *product*, not per page | Module directory under `modules/`. ROOT plus named modules. `antora.yml` labels a component version | Explanation pages are topic-sized. Reference pages follow the code |
| Generated content in the book | `{{#include}}` / `{{#rustdoc_include}}` pull snippets. Preprocessors rewrite Markdown before render | MDX and plugins. Multi-instance exists for versioned product docs, not for mixing an OpenAPI site into maintainer docs | Content sources can sit next to application code via `start_path`. Playbook project holds config, not pages | Reference “can even — to some extent — be generated automatically, but this is never sufficient on its own” |
| CI | `mdbook build`. `mdbook test` runs rustdoc on Rust samples. Link checkers are extra | `npm run build` emits `build/`. Hosting is out of Docusaurus | `antora <playbook>` emits `build/site` | Structure is editorial law. CI is whoever builds the site |

mdBook: a book is Markdown plus `SUMMARY.md`. Prefix chapters (unnumbered) fit a lead page. Part titles split “Cells” from “Law (links)”. The built-in `links` preprocessor expands `{{#include file.rs}}` and line/anchor slices, so a generated graph or a code excerpt can land in a handwritten chapter without becoming the chapter. `mdbook test` is for Rust samples in the book, not for OpenAPI.

Docusaurus: docs are four levels — page, sidebar, version, plugin instance. Multi-instance is for two *products* with different version lifecycles (Android SDK vs iOS SDK). The docs warn that one large instance change rebuilds the other; they tell you to split into two sites when instances are large. That is the same split hive already locked: handbook and OpenAPI do not share an entrypoint. A sidebar `type: 'link'` item can point at an external OpenAPI URL without ingesting the spec.

Antora: closest map to cells. A module is “content related by concept, stage, feature, or other project-specific grouping.” Files live under a content source root next to application code; the playbook is a config-only repo (or folder) that lists those sources. The factory analog is the playbook plus one nav file, not the UI bundle. Hive is one git repo, so Antora’s multi-repo fetch is unused weight. The module idea still holds: one module per cell, ROOT for the entrypoint.

Divio: not a generator. It is the split the factory must keep. Handbook pages are **explanation** (understanding, context, why). OpenAPI is **reference** (describe the machinery, structure around the code, generation allowed, never enough alone). Mixing those two in one TOC is the “collapse” Divio draws: tutorials, how-tos, reference, and explanation fall into one blob. Hive already forbids that collapse at charting (two products, two audiences).

### Large codebases (audience split)

**Rust** keeps four maintainer-relevant products on purpose:

1. *The Book* (`doc.rust-lang.org/book`) — learners. mdBook. rustup opens it with `rustup doc --book`.
2. *rustc-dev-guide* (`rustc-dev-guide.rust-lang.org`) — compiler maintainers. mdBook. About page: “meant to help document how rustc works, as well as to help new contributors get involved.” Search, do not read top to bottom. Links *out* to rustc API rustdoc, Forge, std-dev-guide. Does not embed them.
3. *rustdoc / std* (`doc.rust-lang.org/std`) — crate API consumers. Generated from `///`. rustdoc’s job is “generate documentation for Rust projects” from a crate root or a Markdown file. Public items only by default.
4. *The Reference*, Nomicon, rustc book — other audiences, other books.

`rust-lang.org/learn` is a portal that *lists* those products. It is not a shared book. rustc-dev-guide’s “Other places to find information” list is the pattern: the maintainer book names rustdoc as a sibling, not a chapter.

**Kubernetes** splits user docs, contributor docs, and generated API reference:

- `kubernetes.io/docs` is Hugo in `kubernetes/website`. Page types are Concept, Task, Tutorial, Reference. They cite Diátaxis for how to write each type. Concept pages explain; they do not include step sequences. Reference pages for component tools “generate from scripts.”
- API reference HTML is built from `kubernetes/kubernetes/api/openapi-spec` (OpenAPI) by `kubernetes-sigs/reference-docs`, then *copied* into `website/static/docs/reference/generated/kubernetes-api/v1.NN/`. Bugs in generated docs are fixed upstream in the spec, not in the website Markdown.
- Content guide: “Wherever possible, Kubernetes docs link to canonical sources instead of hosting dual-sourced content.” Dual-sourced content “requires double the effort… and grows stale more quickly.”
- Contributor onboarding lives on a different site: `kubernetes.dev/docs/guide/`. “This document is the single source of truth for how to contribute to the code base.” kubernetes.io is not that document.
- Unpublished config APIs are documented in the *user* reference section (“unpublished APIs which are used to configure kubernetes components… not exposed by the API server in a RESTful way”). Hive law is stricter: OpenAPI is public REST only. Unpublished ports stay out of the consumer spec. A cell handbook page may still *name* Open Host ports and leaving SPIs.

**Go** splits handwritten docs from generated package docs:

- `go.dev/doc/` is the handwritten index: tutorials, Effective Go, spec, contribution guide.
- Package documentation is a separate product. `go.dev/doc/comment`: every exported name gets a doc comment; `go/doc` extracts it; `pkg.go.dev` shows it; `go doc` prints it. The contribution guide is process for maintainers, not package reference.
- Portal vs product: `go.dev/doc` links to `/pkg/`. The generated site is still a different pipeline (pkgsite).

| Codebase | Maintainer entrypoint | Consumer API spec | Generated crate/API docs | Shared homepage? |
| --- | --- | --- | --- | --- |
| Rust | rustc-dev-guide (mdBook) | n/a (language, not HTTP) | rustdoc (`cargo doc`) | `rust-lang.org/learn` lists them; each is its own book |
| Kubernetes | kubernetes.dev | OpenAPI in `api/openapi-spec`; HTML derived into website/static | kubectl/component refs generated from command output | kubernetes.io *hosts* a generated copy under `/docs/reference/generated/`; contributor guide is a different site |
| Go | `go.dev/doc/contribute` | n/a | pkg.go.dev from doc comments | `go.dev/doc` links out; pkgsite is a different program |

Hive is closest to **rustc-dev-guide + a separate OpenAPI artifact**. Not Kubernetes-style “put generated HTML under the same docs tree.” That copy step is how kubernetes.io serves operators who also want the API ref. Hive locked the opposite: factory and OpenAPI do not share an entrypoint.

## Fit to hive

Locked charting already matches the compared split: two products, two audiences; OpenAPI is public REST only; `CONTEXT.md` stays a glossary; law stays in `docs/architecture.md` and ADRs; the maintainer entrypoint links law and does not rewrite it; cells get handbook pages; kernel and `app` get short pages; CODEOWNERS is out.

Factory shape for the spec, still generator-agnostic:

```
handbook sources (handwritten)              consumer pipeline (generated)
──────────────────────────────              ────────────────────────────
TOC                                         OpenAPI from public REST
  entrypoint.md                             handlers only
    lead (plain language)                   unpublished ports stay out
    one-page cell graph
  cells/<cell>.md                           (rustdoc: optional, not factory)
  kernel.md
  app.md
  links: architecture.md, ADRs,
         CONTEXT.md, CONTEXT-MAP.md
```

### Handwritten vs generated

- **Handwritten:** every handbook page. Divio explanation: context, why, what the cell does. rustc-dev-guide tone: search, not a novel. Kubernetes concept page: overview, body, whatsnext; no step dump of architecture law.
- **Generated, not in the TOC:** OpenAPI. Kubernetes builds API HTML from OpenAPI and treats website Markdown as the wrong place to fix spec bugs. Hive should generate and publish the spec as its own artifact (ticket 11), not paste it into a handbook chapter.
- **Generated, optional include:** a mermaid graph of cells, if a later map wants it produced from `app/inproc` rather than drawn by hand. mdBook `{{#include}}` is the hook. Until then, keep the graph handwritten on the entrypoint. Do not generate it from `docs/architecture.md` (that would rewrite law).
- **Not the handbook:** rustdoc. rustdoc documents public Rust tokens (`lib.rs` re-exports: Open Host traits, Published Language types, leaving SPIs, `new`). That is crate-shaped reference. The handbook is cell-shaped explanation. Map item “rustdoc versus the handbook” can close as: keep them separate; do not generate handbook pages from `///`; do not require `cargo doc` as a handbook gate. rustdoc remains available as `cargo doc` for maintainers who want token-level docs. Making rustdoc a merge gate would be a later spec, not this factory.

Kubernetes dual-source rule applies to law: the handbook links `docs/architecture.md` and ADRs. It does not host a second copy. Same for `CONTEXT.md`.

### Entrypoint shape

One file the assembler requires, plus one human start page.

1. **TOC** (mdBook `SUMMARY.md` / Docusaurus sidebar / Antora `nav` + playbook `start_page`). Lists the start page, cell pages, kernel, `app`, then unnumbered suffix links to law. OpenAPI is absent. A sidebar/nav *external link* to a published spec URL is allowed; ingesting the spec is not.
2. **Start page.** Plain-language lead (ticket 01 owns the writing rules). One-page graph of cells (map: the entrypoint holds it; it does not restate ADR 0005). Links to `CONTEXT-MAP.md`. That is the maintainer front door.
3. **Per-cell pages.** One module per cell, matching chapter 2 identity (language, tables, Open Host). Ticket 06 owns sections. Ticket 07 owns disk path. Factory constraint: the TOC must name every cell crate; a cell without a page is a missing chapter, which `build` can fail.
4. **Kernel and `app`.** Short pages. Not cells (chapter 2 kinds). Ticket 13 owns length.

Where files live is ticket 07. Factory-level options that all three generators support:

- Central tree (`docs/handbook/…`) with TOC paths. Simplest for one repo.
- Pages next to crates (`crates/cells/<domain>/<cell>/…`) with the assembler pointing at those start paths (Antora `start_path`, mdBook relative links, Docusaurus `path`). Better colocation, more assembler config.

Either is a factory. Picking one is 07, not this ticket.

### CI (factory slice; 04 owns the gate list)

The factory asks CI for one job: **the book builds**. That is `mdbook build`, `npm run build`, or `antora playbook.yml`. Failure modes that are mechanical, not taste:

- TOC entry with no file (except an explicit draft slot, which hive should not use in production)
- Markdown the generator rejects
- Optional: broken internal links (mdBook documents linkcheck as a separate tool; 04 picks the checker)

OpenAPI generate + drift from handlers is a **second job**. Docusaurus multi-instance warning applies: coupling two large products in one build makes a handbook-only PR rebuild consumer reference. Kubernetes generates API docs in `reference-docs`, then copies; even they keep generation upstream of the website. Hive can skip the copy: publish the spec from the OpenAPI job.

`mdbook test` / rustdoc-on-samples is only worth a gate if the handbook contains runnable Rust. Prefer not to. Handbook examples that must compile belong in tests next to the cell (chapter 10), not in Markdown.

Do not add an LLM prose gate. Ticket 04 already excludes that.

### What the spec should say (and what it should leave open)

Say:

- Factory = TOC + handwritten maintainer pages + `build` in CI.
- OpenAPI = separate consumer artifact, separate job, not a TOC chapter.
- rustdoc = not the handbook.
- Law and glossaries = link, do not copy.
- Site generator = unset.

Leave:

- mdBook vs Docusaurus vs Antora (and MkDocs, etc.).
- Exact handbook path (07).
- OpenAPI crate and annotations (03, 09).
- Gate binaries and OpenAPI drift tool (04, 12).
- Prose rules (01).
- Whether a generated mermaid include replaces the handwritten graph.

No law reopen. Chapter 8 still has no OpenAPI pin; this factory does not add one. Serving Swagger UI from the hive process stays out of scope.
